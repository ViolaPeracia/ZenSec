# ZenSec Roadmap

## ✅ Phase 1 & 2 — shipped

Core cryptography, CLI, OS integration. See `Roadmap.md` history in git for the
original phase breakdown.

## ✅ Phase 3 — hardening (this change set)

Driven by a security audit that found real defects, all reproduced and then fixed
with regression tests.

- [x] **Atomic writes.** Encryption and decryption write to a temporary file and
      rename into place on success. Previously a wrong password truncated the
      destination to zero bytes; a measured 180,000-byte file became 0 bytes.
- [x] **Container version 2.** 54-byte header carrying KDF parameters, the
      plaintext length, and a SHA-256 integrity tag. The header is bound into
      every chunk's associated data, so it can no longer be edited.
- [x] **Truncation detection at chunk boundaries.** The plaintext length is
      authenticated and verified. The previous design depended on the read
      result, which cannot distinguish a full final chunk from a partial one.
- [x] **Appended data is rejected.** Reaching the recorded plaintext length is
      not proof the container ends there. A file whose plaintext was an exact
      multiple of the chunk size previously accepted arbitrary appended bytes.
      Found by reviewing this change set, not by the original audit.
- [x] **64-bit per-file nonce prefix**, up from 32 bits, which made per-file
      nonce collisions likely at around 100k files.
- [x] **Range-checked header parameters**, closing a memory-exhaustion vector
      that storing KDF costs in the header would otherwise have introduced.
- [x] **Output files created with `0600`** on POSIX systems, instead of `0666`.
- [x] **Key material zeroized** on use.
- [x] **Write and close errors checked**, so a full disk no longer produces a
      silently truncated file that reports success.
- [x] **Header errors distinguished** from a wrong password.
- [x] **Version 1 files still decrypt**, verified against golden fixtures
      generated by the original code, with the test suite proving the v1
      re-implementation is byte-for-byte identical.
- [x] **CLI:** `-yes` and `-out` for automation, keyfile size cap, warning on
      trailing whitespace in a keyfile.
- [x] **Test suite:** 25 tests including boundary truncation, chunk reordering,
      per-header-field tampering, hostile KDF parameters, self-reference
      rejection and a fuzz target. `internal/crypto` coverage 89.4%,
      `cmd/zensec` 69.2% (previously no tests at all).
- [x] **CI gates:** formatting, dependency drift, vet, `golangci-lint`,
      `govulncheck`, build, race tests and a coverage gate.
- [x] **Release hardening:** SHA256 checksums and SLSA provenance.
- [x] **Batch scripts** count failures and exit non-zero instead of pressing on.
- [x] **Windows context menu** quoting fixed; it broke on any path with spaces.
- [x] **Documentation corrected.** "Zero-dependency" was false; two modules were
      in use. A threat model was written.

## 🔮 Candidate next steps

None of these are committed. Listed so the decision stays visible.

- **CLI tests to ~90%** and then widen the coverage gate from `internal/crypto`
  to the whole module.
- **Fault-injection seams** for `crypto/rand`, `tmpfs` and `aes.NewCipher` so the
  remaining ~10% of `internal/crypto` — all failure paths — can be covered.
- **Post-quantum option.** AES-256-GCM is not post-quantum. A hybrid KEM or an
  ML-KEM-based container would need a new format version, not a configuration
  change.
- **Streaming from stdin**, which would require dropping the recorded plaintext
  length and therefore giving up boundary truncation detection. Worth thinking
  about before it is worth doing.
- **Code signing for release binaries.** The checksums and provenance attest that
  the build was reproducible and untampered, but there is no signature a user
  can verify without GitHub.
